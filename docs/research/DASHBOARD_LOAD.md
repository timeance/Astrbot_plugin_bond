# 今日概览与分页的合成耗时

合成 SQLite；真实 standings_page 与 PageApi.handle_today_summary；离线宿主日志/认证桩；无 HTTP/JSON 序列化、浏览器或 Provider；三次计时另加一次 SQL 计数，计数不纳入耗时。

Python 3.12.13；SQLite 3.50.4。10群，50人/页；F60/A30/T90；每人一条历史流水，10%成员有当日流水；同Bot两空间总调用固定150初评/30复核。

| 成员 | 分页3次耗时 ms | 分页SELECT次数 | 今日概览3次耗时 ms | 概览SELECT次数 |
|---:|---|---:|---|---:|
| 1000 | [149.32, 165.393, 147.438] | 3003 | [2.823, 3.909, 8.224] | 3 |
| 10000 | [1652.526, 1888.648, 1809.765] | 30003 | [5.95, 8.298, 2.829] | 3 |

空闲时无每日全员衰减扫描。单成员衰减算术O(1)，数据库点查约O(log N)。分页先计算全部候选，再排序和切片；不是只计算返回的50人。样本中每个候选有1次成员读取、2次临时覆盖查询，排序O(N log N)。排行同样先取全部候选计算有效值。

今日概览不读取完整流水；复用成员群键索引和逐群当日时间范围索引、调用日索引。群键枚举仍随成员数增长，当日去重也随当日流水增长，不能称为O(1)。

这是同机合成服务层测量；三次样本不足以代表生产p50/p95。无真实宿主HTTP、浏览器、锁竞争、多进程或大历史库压力验证。

## 代码位置与范围

- `core/decay.py::effective_favor` 按时间差计算，单维算术量固定；没有按成员数执行的每日任务。
- `services/favor_service.py::get` 在读取时给出有效关系，正式写入时结算；临时关系到期的结算属于原有流程。
- `standings_page` 先调用 `standings(..., limit=-1)`，每个候选读取关系与临时状态，再筛选、排序和分页。大量成员时，先优化这里的重复读取比改衰减公式更有价值；本版未重构这一流程。
- `storage/sqlite_backend.py::assessment_day_counts` 按调用日期聚合；`changed_members_count` 按群键与当日时间范围查询流水，使用已有索引。
- 概览在进入总览、切换空间、手动刷新或编辑关系后读取；翻页和搜索不重复查询概览，也不增加定时刷新任务。

结果仅说明本次固定输入下的服务层开销。没有浏览器、真实 Provider、生产数据库或大规模并发验收。
